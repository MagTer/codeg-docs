# 仓库面板

大多数智能体工作的起点，都是有人读完一个 issue，再把它重新敲进提示词里。**仓库面板**省掉了这一步：它把某个文件夹的 **GitHub、GitLab 或 Gitea** issue 和 pull request 列在 Codeg 里，并把你挑中的那一条作为[待办任务](/zh/guide/tasks)交给智能体——它自己的 worktree、它自己的会话，以及在任何东西落地之前那道同样的审阅关卡。

这个功能在 **0.27.0** 中带着 **Beta** 标记发布，而这个标记在 **0.30.0** 摘掉了 —— 因为面板此时已经能走完整个闭环：分标签页读一个改动、在上面评论、开关 issue、以及合并，全程不需要浏览器。**Gitea** 在 **0.30.4** 加入，并顺带带上了 **Forgejo**：Forgejo 是 Gitea 的一个分支，提供同一套 `/api/v1`，所以能和其中一个对话的客户端也能和另一个对话，没有单独的设置项。

自 **0.35.2** 起，面板还能自己完成这次交接。[自动处理](#let-it-pick-items-up-by-itself)会定时扫描仓库，或在 forge 发来 webhook 的那一刻扫描，并把符合你规则的工作项变成任务——和按下**处理**会创建的任务一模一样，也经过同样的关卡。

::: tip 它在整体中的位置
这个面板是通往「待办任务」的一道*前门*，而不是一套并行的系统。它创建的一切都是看板上普通的任务，只是多记录了一个事实：它来自哪一个工作项。正是这份来源信息解锁了最后的交付步骤——也正是它让[自动合并规则](#the-rules-that-do-not-bend)有所不同。
:::

## 打开它 {#open-it}

**仓库面板**位于左侧边栏「待办任务」的下方，也在状态栏的[快捷操作](/zh/guide/workspace#the-layout)中的*导航*分组里。和「自动化」「待办任务」一样，它会接管主区域，右上角有一个**返回箭头**带你回到对话。

它打开时，窗口右上角的按钮簇会多出两个按钮：**刷新**——它重新加载整个列表，而不是缩小列表范围——以及**面板设置**。在真正加载出一个仓库之前，刷新是灰的；设置则永远可用，因为总有一份全局配置可以修改。

## 开始之前，先有一个账户 {#before-you-start-an-account}

这个面板读取的凭据和 git 用的是同一份，在[**设置 → 版本控制**](/zh/reference/settings/version-control)下。选中一个项目文件夹，Codeg 就会去看它的 `origin` 远端：

- **主机三者都不是**——比如 Gitee 或 Bitbucket 远端。面板会说明**只支持 GitHub、GitLab 和 Gitea**并点出主机名，而不是回退到 GitHub、再把错误 API 的答复原样报出来 —— 从前你看到的是「gitee.com 没有 GitHub 账户」或者一段生的 API 失败。**添加账户**仍然提供，因为那是自建实例的另一条入口。
- **有远端，但没有该主机的账户**——空状态会点名提供商和主机，并给出**添加账户**，直接带你去设置页面。

得出这个结论靠的是探测，而不是猜测。名字认不出来的主机会被**直接问一句「你是什么」**，从最便宜的问题开始：

1. **Gitea**，问 `GET {origin}/api/v1/version`。它排在最前，是因为这里只有它既不需要凭据、答案又落在**响应体**里：每一台 Gitea 都公开提供这个端点，并回一个版本对象。一个对什么都回 200 的笼统网关造不出那个形状，所以排除它不用额外花一次请求。GitHub Enterprise（`/api/v3`）和 GitLab（`/api/v4`）则根本不在 `/api/v1` 上挂任何东西。
2. **GitLab**，问 `GET {origin}/api/v4/version` —— 带着令牌时 GitLab 回 200，不带时回 401，而 GitHub Enterprise 会回 404。这两种回答单独都不作数，因为挡在 GitHub Enterprise 前面做鉴权的网关对任何请求都可能给出其中之一。所以 JSON 的 200 或 401 都只是*候选*，Codeg 会拿一条根本没有路由的路径去印证：真正的 GitLab 在那儿回 404，而笼统的网关还是照旧回答，于是 Codeg 拒绝下结论，而不是弄坏一套本来能用的部署。

被记住的是**确定的**答案，在本次进程内有效。主机不可达、或者服务器返回临时性错误，都留着这个问题不作结论，下次再问一遍 —— 一台恰好在重启的 Gitea，在 Codeg 真的听到它说话之前不会被判定为不支持。（Gitea 那一问得到临时性回答，并不会打断 GitLab 那一问：如果后者给出了确定的结论，那个结论算数。）

你在和哪一家 forge 对话，是**由远端在 Codeg 这一侧推导出来的**，客户端无权声称——因为这个选择决定了用哪份凭据。GitLab 的令牌绝不会被花在一次 GitHub 调用上，而一台使用自有域名的 GitHub Enterprise 主机，是按它的 URL 而不是按名字来解析的。

从 **0.27.0** 起 GitLab 有了自己的账户面板，Gitea 则从 **0.30.4** 起；GitLab 的令牌需要 **api** 权限范围，Gitea 的需要 **write:repository**、**write:issue** 和 **read:user**。→ [版本控制](/zh/reference/settings/version-control#gitea-accounts)

## 找到那一条 {#find-the-item}

这个列表是一个分诊台，不是浏览器书签。顶部一排：

- **议题** 和 **拉取请求**——在 GitLab 上则是 **合并请求**，因为 GitLab 用户根本没有 pull request，被告知自己有，读起来就像是走错了工具。每个标签页都会显示当前筛选状态下的数量，而你停在哪一个是**跨会话记住**的 —— 和每页条数并排，理由也一样：它说明的是你在哪个列表里干活。
- **搜索**，覆盖标题和描述。
- **状态**——Open、Closed 或 All。pull request 的行还会在适用时显示 **Merged** 和 **Draft**。
- **分配给我**——一个开关，面板里最快的筛选。
- **标签**——一个可搜索的多选框，取自仓库自己的标签。选的过程中它**保持打开**，因为选两个标签不该跑两趟；仓库一个标签都没有时，它整个都不出现。只列出前 100 个标签，遇到这个上限时它会说明。
- **排序**——最新、最早、最近更新、最久未更新。

分页在底部，带一个**每页**数量选择器（10 / 20 / 30 / 50，默认 20）。有两条限制值得知道，因为面板对这两点都是坦白的，而不是悄悄少给你一些：

- **搜索超时**时，它会说明这一页可能漏掉了一些匹配。
- **只有前 *n* 条匹配可以翻页到达。** 再往后 forge 自己的 API 就不再作答了，于是面板会让你收紧筛选条件，而不是给你一页根本不存在的内容。

点击某一行，它的**详情会在侧边面板中打开**——描述、每一个标签，以及同样的**处理**操作——这样读一个 issue 就不必赔上你的筛选条件、页码和滚动位置。（这个面板展示的是列表已经取回来的内容，而正文在取回时上限为 16,000 字符，所以真正巨大的 issue 还是值得去浏览器里打开。）想看真正的原帖时，**在浏览器中打开**就在那里。

从 **0.28.2** 起，这个面板还会带上**讨论**，而不只是描述——因为在多数 issue 上，描述只是开场，评论才是真正把事情谈定的地方。每条评论都通过与正文相同的 Markdown 渲染器呈现，带上作者、相对时间、只有在 forge 确实记录过编辑时才出现的**已编辑**标记，以及一个指向它的固定链接。**加载更多**继续往下翻。

这些讨论是**在你打开面板时**才去取的，不随列表一起取：把它折进列表，意味着为每一行都花掉一次请求，去画一个读者最多只会打开其中一条的页面。在 GitLab 上，那些事务性事件——*更改了里程碑*、*指派给*——会被过滤掉，所以你读到的就是对话本身，并与行上显示的评论数一致。上百条评论的讨论也能很快打开，因为只画屏幕上那部分，其余的随你滚动再到。

如果某一行的工作项已经有了任务，它显示的就不是**处理**——而是一枚状态标签，点击带你去看板，旁边还有一个小小的**重新触发**链接，用于确实该再跑一次的情形。

### 改动会分成三个标签页打开 {#a-change-opens-as-three-tabs}

issue 仍是一条通栏滚动，因为只有一个标签的标签栏什么也没说明。而 **pull / merge request** 是三个，分支对留在头部，从哪个标签页都读得到：

- **Conversation** —— 描述和讨论，和 issue 一样。
- **Checks** —— CI，并把**最差的状态作为标记放在标签上**，于是构建红了不必点进去也看得见。三种答案被分开而不是糊在一起：绿的、*没有配置任何检查*，以及*这个账户没有权限查看* —— 在 GitHub 上还有第四种「只读到一半」，因为 check runs 和 commit statuses 分属两种权限。
- **Files changed** —— 文件列表，每一行都能打开它自己的 diff；当 forge 给出一个确切数字时，**数量会放在标签上**（改动特别大时 GitLab 报的是被截断的 `1000+`，而不是数字的计数不会显示）。

打开某个文件的 diff **不额外花一次请求**：两家 forge 本来就随文件页一起送来了 hunk，只是 Codeg 从前把它们丢掉了。没有东西可打开的行不可点击。在 GitHub 上它会说明是两种原因中的哪一种 —— 二进制内容，或者因为体积太大被扣下、却仍然统计了行数的 diff。而在 GitLab 上，空的 diff 一律被报成二进制，所以那里请把它读作*没有可用的 diff*，而不是关于这个文件本身的判断。

### 不用离开就能动手 {#act-on-it-without-leaving}

在 **0.29.0** 之前，这个面板只会读。现在它也写：

- **评论。** 讨论下方的一个输入框，以读取该面板的那个账户的身份发出。
- **关闭或重新打开。** 一个按钮，并且**会先确认** —— 与输入框不同，它在你什么都没输入的情况下，一次点击就写进了别人的仓库。
- **新建 issue。** 标题和正文。它会立刻打开，并且**在你眼前这个列表容得下它的时候**不必手动刷新就落进去 —— 也就是 Issues 标签页、第一页、按最新或最近更新排序、没有搜索词、不在*指派给我*、不是仅看已关闭，并且带齐你筛选的每一个标签。其余情形下它只在详情面板里打开，列表保持原样，而不是在你所处的这一页上塞进一行本不该在那儿的东西。

两种写入都**以 forge 的回答为准，而不是假定自己那一下成功了**。发出的评论会带着讨论用于去重的 id、你的令牌实际解析出的作者，以及它的固定链接一起回来。状态变更回来的是 forge 此刻提供的那一行 —— 于是一分钟前别人在浏览器里合并掉的 pull request，落下来是 **merged**，而不是你请求的那个 *closed*。

### 直接在这里合并 {#merge-it-from-here}

打开着的改动不用浏览器就能合并。合并框位于讨论与输入框之间，把你需要拿主意的东西摆出来：**两个分支会不会冲突**，以及 **CI 怎么说** —— 后者只在确实有结论可报时才出现，所以一个没有配置检查的仓库、或者这个账户读不到检查的情形，那里干脆什么都不显示，而不是给你一个让人安心的绿色。

按钮是一个拆分按钮，它的菜单就是**这个仓库自己的设置** —— merge commit、squash、rebase，只在该仓库允许的地方才出现。一个只开了 squash 的仓库只会给你 squash，而不是给一个提交时必然失败的选项。如果这些设置读不到，Codeg 会退回到提供一个普通的 merge，而 forge 仍然可能拒绝它。

::: tip 这和合并一个任务不是一回事
你在[待办](/zh/guide/tasks#merge-it)上按的**合并**，是把智能体的分支落进*你自己的*检出，并且可能需要一个智能体来解决冲突。而这里是**在 forge 上**合并一个 pull request，就像网页界面那样。不同的按钮、不同的地方、不同的含义 —— 来自 pull request 的任务依然完全不能在本地合并。→ [不会松动的规则](#the-rules-that-do-not-bend)
:::

## 把它交出去 {#hand-it-over}

**处理**会打开一个对话框，它的第一个问题正是最要紧的那个：**这件事该怎么处理？** 四种场景，每种工作项两种——你会看到哪一对，取决于你点的是什么。

对于 **issue**：

| 场景 | 智能体被告知什么 |
| --- | --- |
| **直接修复 / 实现** | 先判断这份报告是否成立，然后修掉它定位到的根因——并按这个项目自己的方式验证，构建、测试或 lint |
| **先出方案** | 先判断这份报告是否成立，然后交付一份实现方案——思路、要动的文件、风险、如何验证——然后停下。不改动任何文件 |

对于 **pull / merge request**：

| 场景 | 智能体被告知什么 |
| --- | --- |
| **评审并修复** | 先评判这次改动的方案是否站得住。站得住，就对着基线分支审查它，并就地修好值得修的地方；站不住，就什么都不提交，把评审交还给你 |
| **仅评审** | 给出带位置、严重程度和修复建议的问题清单。**不提交任何东西** |

有三件事，让这些和你自己写的提示词不一样。

**两种 issue 场景都必须先评判这份报告，再动手。** 这不是开场白，而是一个有结果的步骤。智能体被要求复现所报告的行为，或者从代码里指出它在哪里、为什么出错，并给出文件和行号；如果是功能请求，则要确认这个行为是真的缺失，而不是已经以另一个名字或另一个设置存在，并且加上它与这个项目现有的做法相契合。

自 **0.35.2** 起，要问的就不只是*能不能复现*了，因为一份报告描述的事情可能确实会发生，却仍然不成立。以下情形它都不成立：这个行为**无法复现**、在这里**已经修好**、只因**报告者自己的环境或配置**才出现，或者正是**项目有意为之**——报告一个有意为之的行为，那是功能请求，而不是 bug。报告里对原因的说法、以及它建议的修法，都是**有待核实的说法**，而不是指令：一个真实存在、只是诊断错了的问题仍然成立，智能体会去处理它自己找到的那个原因。而当它判断不出一份报告落在这条线的哪一边时——太含糊而无法复现，或者是一个只有维护者才能回答的意图问题——它会被要求按不成立来处理，因为这个判断该由你来下。

在 **0.28.2** 之前，验证曾是一个单独的*仅调查*场景，它被取消，恰恰是因为把它做成一个可选模式，会让「验证」看起来像另外两种流程可以跳过的事。→ [如果报告并不成立](#when-it-turns-out-not-to-be-real)

**审查类场景拿到的是已经检出好的改动。** worktree 起始于 pull request 的 **head 提交**，所以智能体读的、构建的是那份真正的提案，而不是基线分支，它的提交也落在提案*之上*——这正是后面「推回去」这件事说得通的原因。

**审查类场景被要求评判方案本身，而不只是 diff。** *这个改动是否有必要；考虑到这份代码库的其余部分，这是不是最好的解法；就目前这个样子，它能上生产吗？* 而且说得很明白：如果错的是设计本身，就把这一点说出来并提出更好的方案——不要把这个 pull request 改写成那样，因为一次作者从未要求过的重写不叫审查。

**对「评审并修复」而言，这次评判是一道关卡**，自 **0.32.3** 起如此。智能体必须*先*判断方案是否站得住——这个改动到底该不该做，它需要的是不是换一种设计而不是修修补补——当方案站不住，或者智能体自己拿不准时，它**什么都不提交**，连小修小补也不提交。它会说明原因并附上文件和行号，指出应该怎么做，再列出它发现的其他问题，并以这个结论开头。这样收尾算作**成功**，所以这条待办会像其他任务一样回到**等你处理**、交给你验收，而不是带着一堆修补、压在一个终归要推倒重来的设计上。评审进行到一半才发现的设计问题同样会叫停修复，报告里会写明哪些修复已经提交了。

对话框的其余部分：

- **一条可选的额外指令**，只针对这一条工作项。
- **完成后回写评论**——见[下文](#the-comment-that-goes-back)。
- **一份预览**，看到这个任务将会携带的 issue 内容，也就看清了你即将送出去的是什么。
- **一道重复检查。** 如果已经有一个活跃任务在处理这条工作项，页脚会变成**查看已有任务** / **仍然创建**，而不是悄悄再造一个。重启一个所在工作项已有活跃任务的任务，也会以同样方式先提醒你。

创建之后，你得到的就是那个文件夹里一个普通的待办任务，它和其他任务一样，在该文件夹自己的并发上限之下开始。

### 如果报告并不成立 {#when-it-turns-out-not-to-be-real}

有时候，答案是*否*。一个 issue 可能早已被修好、本就是设计如此、只在报告者的机器上出现、描述的是你并不在用的版本，或者干脆没提供足够的信息。

**这会让任务以成功收场。** 智能体被要求什么都不改——连它顺路注意到的小改进也不做——并把决定交还给你：它跑了什么、实际看到的是什么、最可能的解释，以及什么会改变它的结论。自 **0.35.2** 起，它还被要求**在回复开头先给出结论**，只用一行，这样一个提前停下的任务会在结果的最上方就说明这一点，而不是放在最后一段——这是给智能体的一条指令，而不是 Codeg 会去检查的东西。这份结果和其他任务一样落到**待验收**，而*「这份报告不成立，以下是我检查过的全部内容」*就是它的工作成果——接受它就好。如果这份报告点出了此前缺失的信息，把任务连同更多细节退回去，或者交代它照样修掉，它会在同一个 worktree 里接着做。

这个判断也可能在**半路**才落下。如果是做着做着才发现报告终究不成立——这个行为原来是有意为之、报告要求的东西会弄坏项目所依赖的某样东西，或者智能体复现出来的问题其实来自环境而不是代码——它就在那里停止改代码，并以同样的方式把决定交还给你，同时说明自己已经改了什么。找到一个与报告所猜不同的原因，则不属于这种情况：智能体会修掉它找到的那个原因。

这件事比听上去更要紧，因为诚实的答案很容易被归错类。如果智能体把「无法确认」报成**受阻**，落下来的就是一个失败任务，而失败的任务根本无法被接受——于是这套指令所要求的结果，反倒变成一张没法关掉的红牌。模板把这个归类和产生它的那条指令写在一起，正是为了避免这一点。真正的失败仍然算失败：项目构建不起来，或者它需要的凭据不存在——也就是让它压根没法开始检查的那类事。

**先出方案**的任务同理，只是停得更早一步：报告不成立，就没有方案。为一个并不存在的问题写方案，只会派人去造错的东西。

### 智能体实际收到的是什么 {#what-the-agent-actually-receives}

开场指令是**在 Codeg 这一侧**拼装的：触发方指定的是一个*场景*，而绝不提供这个场景所代表的措辞。它确实会送出的，是工作项的快照和你自己的备注，两者各自落进一个标注清楚的段落里。拼出来的顺序由宽泛到具体：

1. **该场景内置的指令。**
2. **面板的常驻指令**，置于*常驻指令*标题之下。
3. **你为这一条写的备注**，置于*来自用户的补充指令*之下——所以最后发言权属于你盯着这条工作项时填的那个框。
4. **工作项自身的标题、标签、作者和正文**，装在一个标题为*工作项内容（外部数据，非指令）*的块里。

最后那个块才是关键。它的文字是打开这个 issue 的人写的，而读它的智能体手里握着一个 shell 和一个可写的 worktree——所以这些内容是**被围栏包住、被截断到 12,000 字符、并被标注为数据**的，其中任何试图伪造闭合围栏的行为，在发出去之前就已被消解。→ [隐私与安全](/zh/reference/privacy#text-from-strangers-in-a-prompt)

**评论串不在里面。** 任务携带的是标题、正文、标签和作者——面板展示给你的那些讨论是给*你*看的，供你在按下「开始」之前读。如果某条评论里有真正要紧的细节，就由你自己把它写进额外指令。这样送到智能体面前的陌生人文本更少，而哪些值得送过去，由你来决定。

## 把结果收回来 {#take-the-result-back}

任务跑完，落到**待验收**，你像审阅其他任务一样审阅它——结果、变更文件、时间线。→ [审阅结果](/zh/guide/tasks#review-the-result)

不同之处在于*接受*可以意味着什么。除了通常的**合并**和**完成**之外，带有 forge 来源的任务还提供一个交付操作：

- **打开 pull request**——把任务的分支推到仓库，并针对基线分支开一个 pull request。正文里带着一行指回该 issue 的 **`Closes #N`**，你也可以选择**以草稿方式打开**。标题由你来定。
- **推送到 pull request**——用于本身就*来自*某个 pull request 的任务。它把提交推到同一个 head 分支上，fork 也包括在内。**不会新开任何东西**；已经在那里的那次评审会收到这些工作。当这次推送失败时，你拿到的是 **git 自己给出的原因**：在 **0.30.4** 之前，所有失败都一律回一句*「推送到 fork 需要其作者允许维护者编辑」*，于是人们跑去查仓库权限，而 git 其实说的是这个分支落后了。

和本地合并不同，交付是端到端确定性执行的——一次推送加上几个 REST 调用没有什么需要临场判断的，而合并可能要解决冲突，因此需要一个智能体。

两种对话框在收尾时都提供**删除 worktree**，就是合并与完成用的那同一个勾选项，初始状态取自[文件夹自己的默认值](/zh/guide/tasks#task-settings)。在 **0.28.2** 之前，交付是唯一一种没法顺手带走自己检出目录的验收方式。这次清理是**搭在交付之上，而不是卡在它前面**：它在任务落定之后才跑，而一次失败的删除只会在卡片上留下一个重试，不会把一个已经推送成功的 pull request 变成一次上报的失败。

::: warning 一个 pull request 是怎么被认领的
在开任何东西之前，交付会先去找一个在 head 提交、head ref、基线 ref 和 head 仓库这**四项上全部匹配**的 pull request。同一个提交完全可能针对不同基线开着好几个 pull request，所以只凭提交哈希会把任务结算到错误的那一个上。共有四种结果：

- **匹配上且已合并**——那**就是**这次交付。任务据此结算，而不是再开一个重复的。
- **匹配上且处于打开状态**——认领它，任务据此结算。
- **匹配上但未合并就被关闭**——任务**退回审阅**。那是一个人做出的决定，引擎不会用重开或复制的方式去推翻它。
- **已经有一个从本分支开往这个基线的 pull request，但它指向另一个提交**——有别人推送过。同样退回审阅，因为新建是不可能的（forge 对同一组 head/base 只允许一个打开的 pull request），而认领又会把任务结算到它从未产出的工作上。

如果什么都没匹配上，交付就会开一个**新的** pull request——这也是一个任务首次交付时的常规情形。
:::

分支是以**触发该任务的那个账户**推送的——而不是「此刻恰好是默认的那个账户」——所以之后把另一个账户设为默认，并不会悄悄改变由谁来执行这次推送。（提交的*作者*是另一回事，由智能体提交时所用的 git 配置决定。）

### 回帖的那条评论 {#the-comment-that-goes-back}

保持**完成后回写评论**开启，任务结算时 Codeg 就会在这条工作项上发出一条评论。它会说明是哪个任务、发生了什么，以及 diff 的计数：

- **在本地合并**进某个分支，附短提交号——这个措辞是刻意的，因为它落在*你自己的*检出里，从未被推送过。对于读这个帖子的其他人来说，那个分支毫无变化，那个哈希也指向不存在的东西。
- **已交付**，附 pull request 的 URL。
- **已完成**但没有落地任何东西。在 **0.32.3** 之前，这一条写的是 *accepted*，放在 pull request 上读起来就像是批准了它；现在它会写明发生了什么——在 pull / merge request 上是 *it made no changes, so nothing was pushed*，worktree 早已不在时则是 *its work was not pushed*；在 issue 上是 *it made no changes* 或 *its work was not merged*。

**智能体写的任何文字都绝不会进入那个帖子**——不是结果摘要，不是提交信息，也不是结论备注。这条评论由任务 id、结果和计数拼出来，而且根本没有一个参数能夹带别的东西。读那个帖子的是别人；智能体对自己工作的评价，不该由他们来接收。

如果这条评论发送失败，时间线也会记下这件事，而不是就此丢掉。

## 面板设置 {#panel-settings}

设置对话框的作用范围和[任务设置](/zh/guide/tasks#task-settings)完全一致——一个**作用域**选择器，其中有一行**全局**配置，即*全部文件夹（全局默认）*，外加可选的**按文件夹**覆盖，由**配置来源**在*使用全局默认*和*单独配置*之间二选一——而且覆盖是**整体生效**的：保存某个文件夹的设置，会让它彻底脱离全局配置，而不是逐字段合并。这条规则是刻意照搬的；这两个对话框只隔着一次点击，不该用两套算术。

自 **0.35.2** 起，表单分成两个标签页。**常规**里放的是这个对话框一直以来就有的内容：

- **Issue 默认处理方式**和 **PR / MR 默认处理方式**——「处理」对话框打开时预选哪一种。它只决定起始位置；随后发出的请求总会明确写出自己的场景。
- **默认回写评论**——那个开关的初始状态，你仍然可以逐条更改。
- **常驻指令**——按场景各一份，外加一个**所有场景**的槽位，会附加到全部场景上。*「用中文回复。完成前先跑一遍项目的测试。」*

常驻指令落在场景内置措辞**之后**、你为单条工作项写的备注**之前**，所以不需要把内置内容再复述一遍。它们**只随任务的开场指令**同行——你希望每一轮都生效的文字，应该写进任务设置的[分阶段提示词](/zh/guide/tasks#add-your-own-instructions-per-stage)里。每一条上限 4,000 字符，超出时会**报错拒绝，而不是悄悄截断**：你敲进去的文字不该不声不响地消失。

**自动处理**是另一个标签页——见[下文](#let-it-pick-items-up-by-itself)。只要表单里它的规则处于开启状态，这个标签上就会带一个小圆点，于是你停在常规页上也能看出它们正在生效。设为跟随全局默认的文件夹则完全不显示标签页；全局规则开着的时候，它显示的是该文件夹的[运行情况](#watch-it-work)，只读，并带**立即扫描**。

## 让它自己接手工作项 {#let-it-pick-items-up-by-itself}

**自动处理**会把匹配的 issue 和 pull request 变成任务，**无需任何人按下「处理」**。每一条走的都正是[「处理」对话框](#hand-it-over)那条路——同样的场景模板、同样被围栏包住的工作项内容、同样的常驻指令和重复检查——所以一个自动创建的任务，就是一个恰好由规则创建的普通待办。它的时间线以*由自动处理创建*开头，这一行还会点明是什么触发了它：*定时扫描*、*Webhook* 或*手动扫描*。

在你打开某个触发方式之前，它什么都不做；它的作用范围也和对话框的其余部分一样：全局配置上的规则覆盖所有跟随全局设置的项目文件夹，而设为**单独配置**的文件夹有自己的一套规则。只有**打开着的项目文件夹**才会被处理——绝不处理 worktree，也绝不处理你已经关闭的文件夹。

### 什么会唤醒它 {#what-wakes-it}

两种触发方式，可以只开一种，也可以都开：

- **定时扫描**——每隔一个**扫描间隔**就把仓库过一遍：1、5、15 或 30 分钟，或者 1、3、6、12 或 24 小时。默认是 **15 分钟**。
- **事件触发（Webhook）**——forge 一报告某个 issue 或 pull request 有变化，就立即扫描。→ [设置 webhook](#set-up-the-webhook)

**webhook 只负责启动一次扫描。** 一次推送里，除了它点名的那个仓库，别的什么都不被信任：随后的那次扫描会用该文件夹自己的账户，从 forge 自己的 API 读取工作项，和定时扫描完全一样。所以两者搭配得很好——webhook 管速度，定时扫描为始终没有送达的推送兜底。

### 它会接手什么 {#what-it-picks-up}

- **Issue**——默认开启，按**直接修复 / 实现**处理，除非你在**处理方式**里选了**先出方案**。
- **PR / MR**——默认关闭，按**评审并修复**处理，除非你选了**仅评审**。**跳过草稿，等它就绪再处理**初始为勾选。

这两个**处理方式**选择只属于这个标签页。它们不跟随常规页上的那两个默认值——那两个只决定「处理」对话框打开时停在哪一项。

**只接手你打开它之后有过动静的。** **包含开启前已存在的条目**关闭时——这是默认值——扫描只会接手自动处理开启以来**新建或有更新**的工作项，开关下方的提示会写明那个时刻。这个时间窗口按 forge 上的*更新*时间计算，所以任何一次更新都会把一个更早的工作项带进来；给它打个标签，就是有意这么做的办法。一次扫描通常只读取上一次扫描之后变化过的内容；修改规则会让下一次扫描退回到那个起始时刻，于是被旧规则跳过的工作项能再被看一眼；而把两种触发方式都关掉再打开，则会让计时从头开始。打开**包含开启前已存在的条目**，所有匹配的未关闭工作项就都在接手范围之内。

**每个工作项最多接手一次。** 只要一个工作项有过任务——无论处于什么状态、已归档，甚至是被你删掉的，也包括你亲手开始的任务——此后它就不会再被碰。你自己从面板上再开始一个，仍然可以。

### 标签与作者规则 {#rules-for-labels-and-authors}

四个列表，每个都是一排胶囊——输入一个模式，按回车：

- **只处理带这些标签之一的条目**
- **不处理带这些标签的条目**
- **只处理这些人创建的条目**
- **不处理这些人创建的条目**

模式不区分大小写，`*` 匹配任意内容：`area/*` 表示所有以 `area/` 开头的标签，`*[bot]` 表示所有机器人账户。其余部分一律精确匹配——`bug` 不匹配 `bugfix`。一个工作项必须通过**每一个填了内容的列表**，**不处理**列表始终优先，空列表则完全不做筛选；没有记录作者的工作项，过不了一个非空的*只处理这些人创建的条目*。每个列表最多 100 个模式，每个最长 200 字符，超出时会在保存时被拒绝，而不是被截断。在某个文件夹自己的设置里，标签输入框会在你输入时提示该仓库已有的标签。

### 它创建的任务会怎样 {#what-happens-to-what-it-creates}

- **立即开始**——默认开启。每个新任务都会立刻排队，何时运行由该文件夹的并发上限决定，就和你在它的卡片上按了**开始**一模一样。关闭时，它会停在**待办**里——除非该文件夹在[任务设置](/zh/guide/tasks#task-settings)里打开了**自动处理**，那样的话，一有空位，看板照样会认领它。
- **完成后回帖**——默认关闭，并且独立于常规页上的那个默认值（后者默认开启）。任务完成时，它会发出与「处理」对话框里那个开关相同的简短状态评论——[只由结果和计数拼成](#the-comment-that-goes-back)。

读取工作项、之后推送其分支的那个账户，是该主机**在扫描创建任务那一刻的默认账户**——此后它就钉在这个任务上，和你亲手开始的任务一样。合并方面没有任何变化：来自仓库工作项的任务依然[绝不会在无人看管时合并](#the-rules-that-do-not-bend)。

### 看它运行 {#watch-it-work}

当作用域是某个文件夹时——无论它有自己的规则，还是跟随全局规则——这个标签页的末尾会有一张**运行情况**卡片：

- **上次扫描**——什么时候、由什么触发，以及四个计数：*列出*（时间窗口内未关闭的工作项）、*匹配*（通过了规则）、*已有任务*和*新建*。
- **新任务**，带编号和标题。
- **跳过**的工作项及原因：*类型不符*、*未开启*、*草稿*、*标签被排除*、*作者被排除*、*无匹配标签*、*作者不在名单*。
- **出了什么问题**，如果有的话——某个未能创建的工作项、一个已创建但未开始的任务，或者一次因错误而中止的扫描，比如缺少账户。
- **下次定时扫描**和**最近一次 Webhook 推送**，在适用时显示。

一次读不完的长列表会被截断，并会说明这一点；下一次扫描会在同一个时间窗口里接着读。**立即扫描**会马上用**已保存**的规则跑一次，所以要等到某个触发方式打开并保存之后它才可用，你做过的任何修改也要先保存。运行情况只保存在内存里，重启后就清空了。

每个数据目录只有一个 Codeg 进程在运行待办看板，而自动处理就在看板所在的地方运行。所以共享同一个目录的桌面应用和服务器不会同时扫描；没有掌管看板的那一方会显示*该数据目录的任务看板由另一个 codeg 进程运行，自动处理也在那里执行，不在这里。*

### 设置 webhook {#set-up-the-webhook}

打开**事件触发（Webhook）**，这个标签页就会给出要粘贴到 forge 里的两个值：

- **Payload URL**——推送的目标地址，以 `/api/forge_webhook` 结尾。在浏览器里，或在连接到远端工作区的桌面窗口里，它就是你此刻正在对话的那台服务器。**桌面应用**只有在它的 [Web 服务](/zh/reference/settings/web-service)运行时才接收 webhook，此时会按该服务报告的每个地址各列出一个 URL；服务停止时，列表为空，并会说明去哪里启动它。
- **密钥**——你打开 webhook 的那一刻就会生成一个随机密钥；这里没有可以自己填写密钥的输入框。眼睛按钮会把它显示出来，**复制**无论显示与否都能复制它，**重新生成密钥**会在下次保存时替换它。关掉 webhook 不会丢掉密钥，所以重新打开时，已经粘贴进 forge 的那个值依然有效。

在仓库的 webhook 设置里，填入这个 URL，内容类型选 **`application/json`**，再填入密钥，并选择 **issue** 和 **pull request** 事件——在 GitLab 上是 **Issues events** 和 **Merge request events**，密钥填作 **Secret token**。代码推送、评论以及其他所有事件都会被确认收到，然后忽略。

**forge 必须能访问到那个地址。** 局域网地址对同一网络里的自建 forge 可用；对 github.com 则不行。forge 访问不到 Codeg 时，请改用定时扫描。

每一次推送都必须证明它知道这个密钥——GitHub、Gitea 和 Forgejo 用的是 HMAC 签名，GitLab 则直接带上 secret token 本身——证明不了的，会在任何其他事情发生之前就被拒绝。每一次答复都是 forge 自己推送日志里的一行，webhook 不工作时就该去那里看：GitHub 的测试 ping 得到 *pong*，被接受的推送得到 *scanning …*，不适用的事件或仓库得到 *ignored* 及原因。→ [隐私与安全](/zh/reference/privacy#webhooks-for-auto-processing)

## 不会松动的那几条规则 {#the-rules-that-do-not-bend}

- **任何由仓库工作项创建的任务都不会自动合并。** 这不是一个你可以打开的设置，而是一条规则。它的提示词里嵌着任意外部用户写的文字，让它在无人看管的情况下落地，就等于铺了一条从注入到主分支的管道。设置了[自动落地已审阅任务](/zh/guide/tasks#let-a-folder-land-them-for-you)的文件夹会整个跳过这些行。对于来自 **issue** 的任务，你自己点的**合并**照常可用——只是必须由人来点。
- **来自 pull request 的任务根本不能在本地合并。** 它的工作属于那个 pull request 自己的分支，作者和评审者正看着那里——把它落到你的基线分支上，等于背着他们把这些改动收编进去：藏在一条本地提交里，而那个 pull request 还开着、看上去尚未合并。因此**合并**被替换为**推送到 pull request**，而且这条拒绝写在后端而不只是按钮上，所以旧客户端或直接调用 API 也一样撞到它。
- **身份在触发时就被钉死。** 由哪个账户读取工作项、推送分支，是在你按下「创建」时决定的——对于[自动创建的任务](#let-it-pick-items-up-by-itself)，则是在扫描创建它的时候——之后改动默认账户也不会移动它。更新那个账户的**令牌**会保住这个身份——[删掉再重新添加则不会](/zh/reference/settings/version-control#github-accounts)。

## 值得知道 {#good-to-know}

- **不做任何镜像。** 这个面板每次都直接读 forge 的 REST API——本地没有你 issue 的副本，刷新是一个按钮。唯一不经你手发生的读取，是你在[自动处理](#let-it-pick-items-up-by-itself)里打开的那些扫描。
- **按文件夹生效。** 面板作用于你选中的项目文件夹，并且会拒绝仓库与该文件夹远端不符的工作项，同时把两者都点出来。
- **这一行可以隐藏。** 如果你不用 forge 集成，在侧边栏的[导航项](/zh/guide/workspace#choose-which-navigation-rows-you-see)里把**仓库面板**关掉即可——快捷操作依然能到达它。
- **自建实例可用。** GitHub Enterprise、自管 GitLab，以及一台 Gitea 或 Forgejo 实例，都按各自的服务器 URL 解析，包括非默认端口或纯 `http://` 的情形，回到工作项的链接也是用同一个来源拼出来的。「不从主机名去猜，而是直接问那台实例」这件事，对 **GitLab 是从 0.30.0 开始**的 —— 从前那种猜错正是以一个光秃秃的 `410` 收场 —— 而针对 **Gitea 与 Forgejo** 的那一问，是 **0.30.4** 才加上的。
- **你配置过的主机，无论叫什么都会去试。** 不带提供商的账户天生是有歧义的 —— 纯 git 凭据对话框写下的字节，和一个老式的 GitHub Enterprise 账户一模一样 —— 所以 Codeg 会去试，而不是为了让消息好看一点，就把一个本来能用的面板拿掉。
