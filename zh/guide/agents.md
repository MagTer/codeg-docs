# 使用智能体

Codeg 不附带自己的模型。它是一个*为*智能体而生的工作区——它连接到你已经在运行的编程智能体 CLI，例如 Claude Code、Codex 和 Gemini，并给它们每一个都提供同一套界面：同一个 composer、同样的文件和 diff、同样的 git 和终端。你选择由哪个智能体处理一段对话，而它周围的一切都保持不变。

本页涵盖要点——启用一个智能体、确认它已准备好运行，以及开启一个会话。相邻的四个页面讲得更深入：[支持的智能体](/zh/guide/supported-agents)是完整名单，[各智能体配置](/zh/guide/agent-setup)逐个介绍每个智能体自己的设置，[认证与模型](/zh/guide/authentication)介绍登录和选择模型，而[自定义智能体](/zh/guide/custom-agents)介绍如何添加名单之外的智能体。

## 智能体的工作原理 {#how-agents-work}

每个智能体都是一个独立的命令行程序。当你开启一个会话时，Codeg 会把该程序作为后台进程启动，并通过 **Agent Client Protocol（ACP）** 与它通信——这种共通的语言让一个工作区能够驱动许多不同的智能体。这正是无论你选择哪一个，体验都保持一致的原因。

Codeg 开箱即支持**十九个智能体**，通过三种方式交付：

- 大多数通过 **npx**（一个 npm 包）运行，因此它们需要你的机器上装有 Node.js。Codeg 会为你安装和更新它们。
- **OpenCode**、**Cursor** 和 **Google Antigravity** 是原生**二进制文件**，由 Codeg 为你的平台下载（Cursor 自带运行时，因此同样无需 Node.js）。
- **Kiro CLI** 和 **TRAE CLI** 运行的是你用厂商自己的安装程序装好的那一份。Codeg 会在你的 `PATH` 上或 `~/.local/bin` 里找到它，从不安装或固定任何一份，而它的**升级**运行的是厂商自己的更新程序。

由于 ACP 是一项开放协议，这十九个并不是上限：你可以自己**注册任何其他兼容 ACP 的智能体**——从该协议的公开注册表，或从它的 distribution JSON——Codeg 会以同样的方式驱动它。→ [自定义智能体](/zh/guide/custom-agents)

对于每个智能体，有两件事是分开跟踪的：它是否已**启用**（允许出现在 Codeg 中），以及它是否已**安装**（实际存在于你的机器上）。二者相互独立——你可以在安装某个智能体之前先启用它，等时机到来时 Codeg 会帮你安装它。

## 启用一个智能体 {#enable-an-agent}

智能体在**设置 → 智能体**中管理（标题为 *Agent SDK Management*）。左侧的**智能体列表**包含每一个受支持的智能体；选择一个即可在右侧查看它的详情。**所有智能体默认都已启用**，因此通常无需开启任何东西——但每个智能体标题栏中的启用开关可以让你隐藏那些你不使用的。右上角的 **+ 添加自定义智能体**按钮，则是你把这份列表扩展到内置十九个之外的入口。→ [自定义智能体](/zh/guide/custom-agents)

只有**已启用**的智能体才会出现在 composer 的智能体选择器中。把那些你永远不会碰的禁用掉，可以让列表保持简短；如果你把所有的都禁用了，composer 只会提示你*打开 Agents 设置*并重新启用一个。这个开关的影响还不止于选择器：你关闭的智能体也会从其他智能体可[委派](/zh/guide/multi-agent)的目标中被剔除。

## 确认它已就绪——预检 {#check-it-s-ready-—-preflight}

打开设置 → 智能体，Codeg 会对每个智能体运行一次**预检检查**——一份快速的健康报告，让你在依赖它之前就知道它确实能运行。你会看到一行**版本状态**——Codeg 推荐的版本与本地已安装版本的对比，即*推荐：… · 本地：…*，或*未安装*；对于你用厂商安装程序装的智能体，则只显示本地版本——随后是一份简短的核对清单，每一项都标记为 **PASS**、**WARN** 或 **FAIL**。

它检查什么，取决于智能体是如何交付的：

- **npx 智能体**——检查 **Node.js** 和 **npm** 是否已安装且版本足够新（每个智能体都设定了一个最低 Node 版本）。
- **OpenCode** 和 **Cursor**——检查你的平台是否受支持、二进制文件是否已下载（OpenCode 还会安装它的插件）。
- **Kiro CLI** 和 **TRAE CLI**——只有一行：检查这个 CLI 是否在你的 `PATH` 上或 `~/.local/bin` 里。版本行随后会显示*本地：…。通过官方安装程序安装；点击「升级」会运行它自带的更新程序。*，或者显示*本机未找到*并附一个**安装指南**链接。
- **ZCode**——检查它的桥接器是否已安装，另有一行 **Official ZCode runtime**，负责找到你的 ZCode 以及一个能加载 `node:sqlite` 的 Node.js 22 或更高版本，取代通常的那几行 Node 检查。

每一项未通过的检查旁边都配有一个**修复按钮**——*安装 Node.js*、*安装插件*等等——版本行还会按需提供**安装**、**升级**或**卸载**；在智能体支持的情况下，还有一个**自定义安装**，用来装你自己选定的版本——Kiro CLI 和 TRAE CLI 只提供**升级**，尚未安装时则只有**安装指南**。当智能体的最新发布版本领先于 Codeg 推荐的版本时，还会多出一个琥珀色的**升级到未经审查的最新版本 …**。→ [支持的智能体](/zh/guide/supported-agents#unreviewed-latest) 在 Codeg 之外改动了什么？**刷新检测**会重新运行预检。

**自己装过某个智能体的 CLI？** Codeg 会认这一点。在它没有自己托管的安装记录时，它会在系统中探测该命令——通过 `npm list -g` 找 `npx` 包、在你的 `PATH` 上找二进制文件，或使用直白的 `--version` 惯例——并报告真实版本，而不是*未安装*。自 **0.35.0** 起，`npx` 智能体的命令还会到 **`~/.local/bin`** 里去找，排在你的 `PATH` 之后、npm 自己的目录之前——Hermes 这类官方安装程序正是把命令放在那里，而从 Dock 启动的桌面应用原本不会去那里找。自己装的 **OpenCode 2.x** 也能连上了：Codeg 会先问它接受哪些启动参数，而不是直接递给它 1.x 的那一套——2.x 会拒绝那一套。既然会话本来就优先使用你 `PATH` 上的安装，这只是让版本行与实际运行的东西保持一致。Claude Code 和 Codex 是例外——Codeg 在这两项上探测的是一个有着自己可执行命令名的 ACP 适配器，而不是你已有的 `claude` 或 `codex`——ZCode 也是例外，它的桥接器还需要你装好的 ZCode 才能工作。→ [ACP 适配器](/zh/guide/supported-agents#acp-adapters)

**而对这些智能体，面板会自己把话说清楚。** *"我终端里明明有 `claude`，Codeg 却说没装"*——这件事足够令人费解，所以 Codeg 就地作答：智能体名称旁边有一个 **ACP 适配器**徽章，而它预检的第一行就是一段 **ACP 适配器**说明，并带有一个**了解详情**链接。它读的是你这台机器的实际情况，而不是照本宣科：如果找到了你自己的 CLI，它会说明在哪里找到的，指出它真正需要的是哪个适配器包，并说明两者可以共存、读同一个配置目录，因此不需要再登录一次。连接失败时也同样具体：它会告诉你缺的是 *SDK* 还是 *ACP 适配器*。ZCode 的那一行则是替它的桥接器说话：它会写出 Codeg 运行的那个包，并请你先安装并登录官方 ZCode。→ [ZCode](/zh/guide/agent-setup#zcode)

::: tip 预检检查的是底层环境，而非登录
预检确认的是运行时、版本和安装情况——而不是你是否已登录。让一个智能体完成认证（用它自己的订阅、一个 API 密钥或一个自定义端点）是一个单独的步骤。→ [认证与模型](/zh/guide/authentication)
:::

### 当 Codeg 与你的终端说法不一致时 {#when-codeg-and-your-terminal-disagree}

有时某个智能体在你的终端里运行得很好，但 Codeg 却坚称它没有安装。这几乎总是 **PATH 差异**：从程序坞启动的桌面应用不会像终端那样继承 shell 的配置，因此由 `nvm`、`fnm` 或 Homebrew 安装的 Node 对它来说可能是不可见的。

**诊断**——位于预检列表旁边，以及会话被拦截时出现的横幅上——会运行**环境诊断**来查明原因。它探测的是*应用本身*如何解析这些内容，而不是你的 shell：它看到的 Node 和 npm、npm 全局前缀、它在哪些位置查找过该智能体的可执行文件、任何版本管理器目录，以及最有用的部分——**与你的登录 shell 的对比**，列出你的终端有、而应用没有的那些 PATH 条目。它最后会给出一个直白的判断，例如 *"该命令在你的终端中能解析，但在应用中不能——这是 GUI PATH 差异"*，并常常给出具体的解决办法，比如彻底重启应用。自 **0.35.0** 起，当只有你的终端找得到这条命令、别处都找不到时，你得到的也是这个判断，而不是一句干巴巴的*未安装*；Node.js 检查也会比对智能体所需的**完整**版本号，所以 Node 20.2 不会再被当作满足一个要求 20.3 的智能体。**全部复制**可以把整份报告放到剪贴板，便于提交问题反馈。

预检会在你每次打开该界面时自行运行；而诊断是当预检与实际情况不符时，由你自己运行的更深层探测。

## 配置一个智能体 {#configure-an-agent}

大多数智能体一经安装就能工作，但每个智能体的详情面板都有许多可供你调整的地方——而且有两种方式来做：用**可视化控件**处理日常设置，或用智能体的**原始配置文件**处理任何 UI 未暴露的内容。

- **可视化设置。** 面板将常见选项以普通表单控件的形式呈现——登录、模型选择、自定义端点、推理强度，以及每个智能体自己的各种开关——因此你很少需要手动编辑任何东西。登录和选择模型在[认证与模型](/zh/guide/authentication)中介绍，每个智能体的面板里有些什么，则见[各智能体配置](/zh/guide/agent-setup)。
- **环境变量。** 在智能体启动时传递给它的 `KEY=value` 键值对。
- **配置管理。** 如果智能体有自己的原生配置文件（它的*原生 JSON 配置*），可以直接从 Codeg 编辑它，用于处理可视化控件触及不到的设置。
- **拖动可重新排序。** 智能体列表的顺序同时也是一种偏好设置——当没有指定其他智能体时，第一个已启用的智能体就是 Codeg 会选用的那个（详见下文）。

在会话打开期间更改某项设置，该会话会继续以它旧的配置运行——Codeg 不会在任务中途打断你。取而代之的是，一个横条会出现在**对话顶部**，提示它仍在使用先前的配置；点击**重连以应用**，会话就会带着新设置重新加载，同时**保留其完整历史**。无需关闭再重新打开任何东西。

::: tip 当智能体不接受某项设置时
composer 里提供的一部分选项其实是一次*请求*，而不是命令——智能体会回复它实际采纳了哪些。挑一个某个智能体不接受的模型或模式，以前看起来就像这项设置莫名其妙地弹了回去。现在 Codeg 会说明它实际采纳的是什么，并**保留你的偏好供下次使用**：一次拒绝往往只针对*这一个*会话，而不是这个选择本身——一次在对话中途被拒绝的模型切换，换到新会话里常常就成功了。
:::

### 让智能体自己处理文件和命令 {#let-the-agent-handle-its-own-files-and-commands}

通常情况下，智能体的文件读取、文件写入和终端命令都由 Codeg 通过协议代为执行。这很方便——但它意味着这些操作跑在 **Codeg** 的进程里，落在智能体给*自己*套的那层沙箱之外。一个配置了「拒绝读取 `**/.env`」的智能体没法对一次由它委托出去的读取执行这条规则：它自己的审计日志会记录该策略已应用、无违规，因为它所控制的一切从来没有真正接触过这次访问。

每个智能体页面上、环境变量编辑器旁边的一个开关——**让智能体自己处理文件和命令**——会把这三样交还给它。此时 Codeg 两个通道都不再通告，即便被调用也会拒绝，于是智能体在自己的规则之下做自己的 I/O。

它**默认关闭**，原因就写在开关上：*Codeg 自身不提供沙箱，因此只有当智能体确实配置了沙箱时才打开它。* 大多数智能体并不带沙箱，所以对它们而言，打开这个开关只是用一个能用的文件通道换来了什么都没有。

::: warning 它同时会收走委托能力
打开它会为该智能体去掉**委托**工具，因为 `delegate_to_agent` 是通往同一个房间的第三扇门——它让 Codeg 在自己的进程树里再起一个智能体，再把输出转发回来，而这恰恰就是这个开关要堵上的那处泄漏。[多智能体协作](/zh/guide/multi-agent)面板会**点名这条规则当前适用于哪些智能体**，而不是在工具其实没发过去的时候仍显示「已启用」。在该智能体的环境变量里设置 `CODEG_ACP_HOST_TOOLS=agent` 效果相同。→ [配置](/zh/getting-started/configuration)
:::

## 开启一个会话 {#start-a-session}

开启一个新对话，composer 会显示一个**智能体选择器**——一排药丸形按钮，每个已启用的智能体一个。点击其中一个，Codeg 就会连接到它；接着，从 composer 里的[智能体设置按钮](/zh/guide/conversations#start-a-session-—-the-composer)设置**模型**、**模式**以及该智能体的其他选项。这些全都来自**智能体本身**，而非 Codeg，因此可供选择的内容取决于你正在运行哪个智能体。你对智能体的选择会在你发送第一条消息后锁定——一段对话会一直由开启它的那个智能体来处理。

**默认用哪个智能体？** Codeg 按以下顺序选择：

1. 文件夹的**默认智能体**，如果你设置过的话（文件夹菜单 → *设置默认智能体*）。
2. 否则，就是你在设置 → 智能体中排序里的**第一个智能体**。

因此，按文件夹设置的默认值总是优先，而列表顺序是后备方案。→ [工作区](/zh/guide/workspace#folders-and-the-sidebar) 介绍了如何设置文件夹的默认值。

当你第一次在会话中使用某个智能体时，你会看到**连接中...**，此时 Codeg 正在启动 CLI 并完成握手。自 **0.35.2** 起，这时你仍然可以改主意：选另一个智能体，正在启动的那个会被立即停止，最终连接的是你最后选的那一个。如果它无法连接——智能体被禁用、未安装、在你的平台上不受支持，或响应缓慢——Codeg 会发出一条**告警**：一条说明出了什么问题的 toast，带有**重试**，需要去设置里修复时还会带上**打开 Agents 管理**。之后这条告警会留在状态栏的**告警**列表里，只是不再带**重试**。composer 下方的连接心形也会变红，并说明原因。

## 连接状态 {#connection-status}

在你工作时，composer 下方的**连接心形**会显示智能体的状态——已连接、连接中、连接异常或未连接——并在它的弹出面板里把*响应中…* 与静止的*已连接*区分开。点击它可以查看详情，以及一个**重新连接**——它会尝试恢复原会话。如果智能体无法加载会话，或者加载失败，Codeg 会改为在同一个对话上开启一个新的智能体会话：对话记录还在，但智能体已不再拥有之前的上下文。→ [当连接看起来不对劲时](/zh/guide/conversations#when-the-connection-looks-wrong)

你没有在看的会话可能会在闲置几分钟后断开连接以释放资源——后台工作仍在运行时不会，开启了[远程控制](/zh/guide/conversations#continue-on-your-phone-—-remote-control)的 Claude Code 会话也不会——但你正在活跃使用的标签页会保持连接，而当你回到某个会话时，Codeg 会**自动重新连接**。
