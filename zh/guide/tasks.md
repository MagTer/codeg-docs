# 待办任务

对话是你得坐在它面前的东西。**任务**则是你写下来之后就可以走开的东西。

**待办任务**就是这样一个队列，智能体会自己一件件做完。每个任务都会拿到**一份独立的代码副本**——项目旁边的一个 git worktree——因此可以同时跑好几个，既不会互相干扰，也不会打扰你手头正在改的那份代码。某个任务做完后，它不会自行合并：它会移到验收那一列等你过目。你读一下 diff，或者打回去让它改，或者点通过——只有到这时候，它才会落到你的分支上。（你也可以让某个文件夹[自己把已验收的任务落地](#let-a-folder-land-them-for-you)，但在你主动要求之前它是关闭的。）

## 任务是什么 {#what-a-task-is}

一个任务就是一个标题、一段描述，以及用来执行它的 composer 状态——一个智能体、一种模式，以及该智能体接受的各种选项。仅此而已。其余的一切由 Codeg 提供：隔离的检出、分支、调度，以及末尾那道验收关卡。

它沿着一条固定的流水线推进：

```text
待办 → 排队中 → 初始化中 → 进行中 ⇄ 等待输入 → 待验收 → 合并中 → 已完成
```

**失败**和**已取消**是从它旁边岔出去的支路。全程有两条规则成立。**「已完成」只由两处写入**——一次经 git 核实确实落地的合并，以及对没有东西可合并的任务点[**完成**](#review-the-result)——而一旦写入就绝不回退。以及**任务绝不会跳过验收这一停顿**：通往已完成的每一条路都要经过它，自动合并也不例外。

这正是任务与它旁边那两样东西的区别所在。[对话](/zh/guide/conversations)是你和一个智能体一轮一轮地聊，在你自己的工作树里。[自动化](/zh/guide/automations)是一个按时钟触发的会话。任务两者都不是：它是一份工作单元，有明确的起点、一个用来发生的隔离场所，以及末尾的一道验收关卡。

## 打开待办任务 {#open-the-board}

**待办任务**位于左侧边栏，在自动化下方。它像自动化一样接管主区域——标题开头的**返回会话**按钮可以带你回到会话，你原先打开的标签页依旧在那儿——并在有任务等着你时带上一个小小的**计数徽标**：凡是处于*等待输入*、*待验收*或*失败*的任务都算——你[留到以后处理](#set-it-aside-for-later)的和已归档的除外——因此你在任何界面上都能看出有东西需要看一眼。

自 **0.37.0** 起，你不一定非得打开这个页面：右侧面板的**待办任务**标签页会把你所在项目的看板显示为上下堆叠的几个分区，带搜索、**新建任务**，以及看板上的每一个卡片操作和对话框。拖动、列表视图和任务设置仍只在这里。→ [右侧面板](/zh/guide/side-panel#the-project-s-automations-to-dos-issues-and-pull-requests)

它自己的两个控件位于**窗口右上角那一簇**，就在设置齿轮旁边：一个**视图切换**，一个**任务设置**。它们不占额外宽度——整页路由本来就会隐藏终端与辅助面板开关（此刻它们无处作用），这两个按钮正好接管那两个位置。

### 看板还是列表 {#board-or-list}

**看板**分为四列：

| 列 | 里面是什么 |
| ------ | ------------ |
| **待办** | 已写下但尚未开始——以及所有卡在并发上限后面排队的、和定时到点才开始的任务 |
| **进行中** | 正在初始化，或者智能体此刻正在处理它 |
| **等你处理** | 卡在提问上、已完成待验收、正在合并，或者失败了 |
| **已完成** | 已合并，或没有东西可合并而直接完成（以及在你要求显示时的已取消任务）——还有你[留到以后处理](#set-it-aside-for-later)的任务，带着一个灰色的**以后处理**标记 |

每一列都按**最近更新在前**排序，所以刚刚移动、重试或完成的任务就在列首，而不是被更早的工作压在下面。

**列表**则把同样这些任务排成一张扁平的表，同样最近在前——**状态 · 任务 · 位置 · 变更 · 更新**——并带一个说着那四个列名的**状态**筛选器——留到以后处理的任务在那里同样算作*已完成*。列表的每一行会把它所提供的操作全部显示为带说明的图标按钮，而不是把大多数藏进溢出菜单里，因此当任务多到四列装不下时，列表是更快的那一面。你选的视图会被记住。

卡片上先是状态，然后是一行元信息：*文件夹 / 分支 · `+`/`−` 行数 · 一个相对时间*。最后这一项是任务真正抵达过的最近一个节点——已完成或已取消，否则是待验收或失败，否则是开始执行，再否则就是被创建。而在任务处于活动状态时，卡片还会带上**智能体最近上报的进展**，因此不必打开任何东西，这一列就能告诉你正在发生什么。点击卡片可打开它的详情抽屉——从 **0.28** 起它从右侧滑入，而不是盖住看板，因此你正在看的那一列仍留在它背后。卡片右侧的圆形按钮是它的操作。

标题旁边是**正在处理它的那个智能体的标识**——解析方式与运行本身完全一致，因此一个从未指定过智能体的任务显示的是它所在文件夹的默认智能体，也就是真正会被启动的那一个，而不是一片空白。当看板上同时有三个智能体在干活时，这就是「扫一眼这一列」与「逐张卡片打开」之间的差别。

## 添加一个任务 {#add-a-task}

**新建任务**会打开编辑器：

- **标题**——*要做什么？*
- **任务描述**——完整的 composer，与你在对话中使用的是同一个：`@` 引用文件，`/` 唤起命令，`$` 唤起 Codex 技能，**+** 菜单里还有技能与快捷消息，以及**附件**。一份 bug 报告可以就是一张截图，别的什么都不写。
- **目标**——它运行所在的项目文件夹。这里只会提供**项目根目录**；任务不能以某个 worktree 为基础，因为它自己会创建一个。已经跑过的任务会被固定在它的文件夹上。
- **基准分支**——任务从哪个分支出发，最后也落回哪个分支。不去动它时，它显示 **HEAD**，旁边是你的项目文件夹当前所在的分支，含义是*任务开始时的当前分支*；从列表里选一个本地分支，就能固定成另一个。任务一旦有了 worktree，它就固定下来；而来自 pull request 的任务不会问这一项，因为它从那个 pull request 出发。
- **智能体及其设置**——这些起初都处于*继承自任务设置*，并会一直如此，直到你动它们为止。智能体就是描述上方那枚药丸形按钮；自 **0.37.0** 起，它的模型、模式和其他选项都集中在描述框底栏的一个**智能体设置**按钮上——与[对话的 composer](/zh/guide/conversations#start-a-session-—-the-composer) 用的是同一个按钮、同一个面板——而不再是每个选项各一个下拉框；按钮上显示的就是将要保存的内容：你选的值，没选则是该智能体当前的值。为本任务覆盖其中一项后，会出现一个**恢复继承**的控件把它还回去。自 **0.33.0** 起，智能体下方的那行字会说明你拿到的是哪一种情况。当任务设置里没有指定智能体，或者指定的智能体在这里不可用时，选择器仍会显示一个你能运行的智能体——而且它会**随任务保存**，所以你看到的智能体就是实际运行的那一个。以前，它可能显示一个根本没被保存的智能体，任务随后就以 *no agent configured* 启动失败。

而且这不只是新建任务那个框。**每一个待办输入框都是完整的 composer**——编辑任务、对已验收的任务继续处理、给重试留一段说明——所以无论你在哪里打字，都能引用文件或粘贴一张图。

**模板**把一整个任务保存为蓝图：**把当前内容存为模板**会以一个名字存下标题初值和所捕获的 composer 状态，而从列表中选一个则会用它重新填充编辑器。用一个已用过的名字保存会就地更新那个模板，而不是堆出一堆副本。

另外还有三扇门通向这里：

- **来自一条消息。** 读回复时发现了一个后续要做的事？任意消息的复制按钮旁边就有**由此消息创建任务**——它会把那段文本放进一个新任务，并预先填好项目文件夹，然后把你切到待办任务。
- **来自一个自动化，或者智能体自己。** 自动化可以不启动会话，而是排入一条任务；而在你允许之后，对话中的智能体也可以自己排一条。→ [自动化](/zh/guide/automations#choose-what-a-fire-does)
- **来自一条 GitHub、GitLab 或 Gitea 工作项。** [仓库面板](/zh/guide/repository)列出你的 issue 和 pull request，并把其中一条直接交给智能体，同时选定该如何处理——直接修它、先出方案、评审它并修复发现的问题，或者只评审它。自 **0.35.2** 起，它还能**自己**创建任务：定时扫描，或在收到 webhook 时扫描，找出符合你规则的工作项；这些任务的时间线以*由自动处理创建*开头。无论哪种方式，产出的任务都是这块看板上普通的一条。→ [仓库面板](/zh/guide/repository#let-it-pick-items-up-by-itself)

## 让它跑起来 {#set-it-running}

除非你发话，否则什么都不会自己开始。有三种方式启动一个任务：

- 卡片上的**开始**。
- 把一条待办**拖**到*进行中*那一列——当指针进入时，它会显示*松开即开始执行*。
- 给它**定一个时间**——见下文。

无论用哪种方式，**并发上限**都会生效：超出上限的任务会停在*排队中*，等有空位时再开始。这个上限按文件夹计算，默认为 **2**。

*排队中*就只是这个意思，不多不少——在等一个空位。一旦拿到空位，任务就会转到*进行中*列里的**初始化中**，此时正在创建它的 worktree、执行它的初始化命令；一个装了三分钟依赖的任务本来就该待在这儿。整个过程都可以取消，而且取消是真的会中止安装，不会把 `pnpm install` 丢在后台跑完。

在任务设置中打开**自动处理**，你就什么都不用按了——待办会在有空位时自行认领，这条队列也就真正变成了一条工作队列。[仓库面板的自动处理](/zh/guide/repository#what-happens-to-what-it-creates)是另一个常驻的*开始*：只要它的**立即开始**开着（默认就是开着的），它创建的每个任务一出现就会进入队列。

*待办*列中的卡片还可以**拖动排序**，而这个顺序正是自动处理器所遵循的。（排序需要选中单个文件夹——顺序是按文件夹存储的，混合文件夹的一列没有任何可以持久化的东西——而且在[搜索](#keep-the-board-tidy)正在收窄看板时，排序不可用。）

### 让它在你指定的时间开始 {#start-it-at-a-time-you-pick}

待办卡片上的**定时运行**要你选一个日期和一个时间。任务会原地待到那一刻，然后**就像你亲手按了「开始」一样**启动——文件夹的并发上限依然决定真正能启动多少，所以定时是一次「到点请开始」的请求，而不是插队的承诺。

对话框**打开时是空的**，这样一个从未安排过的任务就不会看起来像被安排过；日历旁边还有*1 小时后*、*3 小时后*和*明天 9:00*。选好日期后它会替你填一个合适的钟点——当天就填下一个整点，隔天则填 09:00——而不是留给你半个存不下去的值。定好的卡片会显示*计划于 …… 开始*；**清除定时**可以把它撤掉。

有三处边界值得知道：

- **Codeg 关着的时候错过的时间点，会在下次启动时触发**，而不是被悄悄跳过。
- **你亲手按「开始」会接管这个计划。**
- **取消任务会一并清除它的定时**，因此之后重新排队时，不会被一个你早已忘掉的时间点唤醒。

## 一次运行究竟做了什么 {#what-a-run-actually-does}

任务开始的那一刻，在任何智能体介入之前：

1. **创建一个 worktree**——目录为 `<项目>-task-<id>`，分支为 `task/<id>`——并钉在你项目 HEAD 当时所指的那个确切提交上，因此中途切换分支也无法让它漂移。默认它就落在你的项目旁边，你也可以[把它们统一放到别处](#keep-the-worktrees-somewhere-else)。这个 worktree 会在该任务之后的每次运行中被复用。
2. **运行初始化命令**（如果文件夹设置了的话，比如 `pnpm install`）。它只在*新建的* worktree 中运行，绝不会在复用的 worktree 上重跑；非零退出码会**中止本次启动**，而不是让智能体在装了一半的环境里开工。出于同样的理由，被中断的安装——你取消了，或者 Codeg 退出了——下次会重新执行。
3. **启动智能体**，工作目录就是那个 worktree，输入是你的任务描述，外加一条常驻指令：尽管往任务分支上提交，但**不要**合并进、变基到或推送基线分支——结果由用户在验收之后落地。

从这里开始它就是一个真实的智能体会话，并且会产生一次真实的对话，你可以在侧边栏中该 worktree 文件夹下找到它。

在它工作期间，智能体多出两个只存在于任务运行中的工具：

- **`task_progress`**——一行进展里程碑（*"测试通过了，开始清理"*），会实时出现在卡片和推进记录上。
- **`task_complete`**——结论，在最后调用一次：**success**（成功）、**needs_review**（能用，但这一处请看一下）或 **blocked**（做不下去，以及为什么）。success 和 needs_review 会把任务送去验收；blocked 则把它标记为失败。

两者都会以卡片的形式出现在任务的对话里。自 **0.37.0** 起，展开其中一张会显示经过排版的完整消息或摘要，另有一行说明它是否**已记录到待办任务**——以前 Claude Code 和 Codex 在这里只显示一个光秃秃的 `{"recorded":true}`。

::: tip 这两个工具与协作设置的开关无关
`task_progress` 和 `task_complete` 只会注入到任务运行中，因此它们不依赖委派、实时反馈或[设置 → 协作](/zh/reference/settings/collaboration)中的任何东西。而且它们只是建议性的：即便智能体从未调用 `task_complete`，任务仍会在其回合结束时正常落定——进入验收，除非这一回合[以智能体错误告终](#when-a-task-needs-you)。
:::

## 当任务需要你时 {#when-a-task-needs-you}

任务会因为四种不同的原因落到**等你处理**，卡片上的状态会告诉你是哪一种：

- **等待输入**——智能体卡在一个权限请求、一道选择题，或一次计划批准上。在你回答之前什么都不会推进。如果任务的智能体做了[委派](/zh/guide/multi-agent)，卡住的是**子智能体**时它同样会这么说，而不是停在「运行中」却什么都没发生。
- **待验收**——它做完了。见[下文](#review-the-result)。
- **合并中**——合并正在进行。这是唯一一个你无法取消的状态。正在等待合并档期的任务显示的则是**排队合并**——见[下文](#a-second-merge-waits-in-line)。
- **失败**——运行出错、被重启打断，或者智能体报告了 **blocked**。自 **0.35.2** 起，这也包括**以智能体错误告终**、除此之外什么都没留下的一回合——比如一次工具调用被截断之后上游返回的 `400`，它仍会像正常完成那样结束这一回合：没有回复、没有改动、也没有结论，任务就会失败，卡片上显示**智能体自己的报错信息**，取其最后 4,000 个字符。以前它会悄无声息地滑进*待验收*，或者，对于以其他方式停下的回合，只说一句智能体停止了。写出了回复、改动了文件或报告了结论的回合，仍会像以前一样进入验收。**重试**会在同一个 worktree 中接着做，并被告知上一次尝试被中断了、请继续；你还可以给这一轮补上一段**说明**。

**查看会话**是你解开第一种情况的地方。它会打开该任务智能体会话的只读实时视图——虽然对*发送提示词*而言是只读的，但它确实会渲染权限对话框和提问卡片，所以你就是在这里作答。对于运行中的任务，这个视图是实时流式的；对于已落定的任务，它显示存下来的记录，并按任务经历过的阶段分段：**任务执行**、**重试执行**、**继续处理**和**合并变更**。它会**嵌套在打开它的那个任务抽屉内部**，因此从记录里退出来会回到任务本身，而不是回到一片空白。从 **0.30.3** 起，记录里提到的文件会**在它旁边打开**，而不是打开在被看板挡住的那一栏工作区里 —— 点文件徽章、Markdown 链接或**查看差异**，会在消息旁边弹出一个只读预览，**在工作区中打开**也只有一步之遥。→ [画布上的同一个面板](/zh/guide/canvas#a-card-is-a-real-conversation)

### 留到以后处理 {#set-it-aside-for-later}

*等你处理*里的东西，并不都值得今天就花心思。自 **0.36.0** 起，**待验收**或**失败**的任务——被中断的也算——提供**以后处理**：卡片和列表行上是一个时钟按钮，抽屉里也有这个操作。任务会原样移到**已完成**，带着一个灰色的**以后处理**标记，悬停提示会写出它真实的状态——比如*以后处理 · 待验收*——并且不再计入徽标。除此之外什么都不变：它的状态不动，它的 worktree 和会话也都留在原处。

回来也一样快：

- 对一个留到以后处理的待验收任务，**继续处理**是首选操作。在卡片上，它会打开一个对话框，里面的四种[意图](#say-what-kind-of-follow-up-you-mean)和抽屉里的跟进一样；发送后任务会立刻重新开始，卡片随即回到*进行中*。
- 留到以后处理的失败任务照样可以**重试**。
- **移回等你处理**会去掉这个标记，把它放回原来的位置。

用其他任何方式了结它——合并、*完成*、推回 forge、*放弃*、一次跟进或一次重试——同样会去掉这个标记；一次弹回来的合并会回到*等你处理*。有两件事会刻意不碰留到以后处理的任务：[自动合并](#let-a-folder-land-them-for-you)会跳过它，**全部归档**也会绕开它。处于*等待输入*、*合并中*或*排队合并*的任务不提供这个操作——一个仍在运行的智能体或一次正在进行的合并，都不是能往后放的事。

### 如果它的 worktree 不见了 {#if-its-worktree-went-missing}

把一个任务的检出目录从磁盘上删掉——手工删，或者从[分支选择器](/zh/guide/git#work-in-parallel-with-worktrees)里删——这个任务以前就无路可走了：合并需要 worktree，而「完成」当时只在没有改动时才提供，并且会因为目录不存在而报错。现在它能自己恢复：

- **每张卡片都会标注**，无论处于什么状态，都会显示 *Worktree 已删除*。
- **待验收的卡片会把「合并」换成「完成」**，对话框的文案会说明原因。若工作分支上仍有未落地的提交，该分支会被保留，而不是被删掉。
- **重试或继续处理会重建检出**——依据任务记录下来的分支，在它原本的基线上重建——因此已提交的工作会被重新接上，而不是被晾在一棵崭新的空树后面。

## 验收结果 {#review-the-result}

打开一个待验收的任务，详情抽屉会把你判断所需的一切摆出来：

- **结果**——智能体在调用 `task_complete` 时写下的摘要，按 Markdown 渲染，因此其中的标题、列表和代码都会正常显示。内容较长时会折叠在**展开**之后。
- **变更文件**——相对于任务所记录基线的每一个文件，带 `+`/`−` 计数。点击其中一个看它的 diff，或用**查看全部差异**一次看完。
- **这些计数衡量的是*这个任务*干的活。** 从 **0.28.2** 起，它们锚定在验收时交付的那个起点上——对于从 pull request 触发的任务是该请求的 head，否则是记录下来的基线；当分支把基线的改动合了进来时，锚点还会前移到当下的 merge base。于是从 pull request 触发的任务不会再把该 pull request 自身的改动算成自己的成果，而一个合入过基线的分支也不会把基线的改动算进来。（列表仍保留更宽的 merge-base 视图，并会在其中包含 pull request 自身改动时就地说明。）智能体新建但从未暂存的文件也会被算上：`git diff` 是从索引里枚举路径的，所以全新的文件此前会读成*根本没干活*——现在这套度量跑在一份用完即弃的索引副本上，既能看见这些文件，又不碰你真正的索引，也不会把被忽略的产物算进来。
- **推进记录**——这个任务的时间线：创建、状态变化、实际生效的启动配置、初始化命令的输出、智能体的里程碑与结论、预检、合并尝试，以及你自己的操作。
- **详情**——分支、有了之后的合并提交、变更总量、计划开始时间，以及创建 / 开始 / 完成的时间戳。总 token 用量在标题栏中。

如果文件夹设置了**预检命令**，它会在任务抵达验收的那一刻在 worktree 中运行——这就是你的验收测试，在卡片上表现为一盏红灯或绿灯。失败时它会把输出的末尾就地保留下来，于是你不必打开终端就能看到是哪里坏了。

出口有四个：

- **合并**——通过。见[下文](#merge-it)。
- **继续处理**——再来一轮。见下文。
- **完成**——直接标记为完成，完全不做合并。当任务**没有改动任何文件**时提供——它只是回答了一个问题，或者核实了本来就没问题的工作——因此没有东西需要落地，也不会产生一条空的合并提交。是否保留它的 worktree 仍由你决定。
- **放弃**——不合并就丢掉，并可以顺手把**原因**记到时间线上。任务转为已取消；从 **0.30.0** 起这个对话框可以顺手把 worktree 一并带走，于是一次真正意义上的放弃能在一个动作里把磁盘收回来。这个勾选项默认**不勾**，并且刻意*不*从文件夹的删除 worktree 默认值取值 —— 那个默认值关心的是把已完成的工作落地，而一个已取消的任务还可能被**重新排队**，并且这次清理会连同工作分支一起删掉。不勾也不会有东西被撂在半路：抽屉之后会单独提供这次移除。

或者先把决定往后放：**以后处理**会把它原样移到*已完成*，等你准备好再说——见[上文](#set-it-aside-for-later)。

来自[仓库面板](/zh/guide/repository)的任务还有第五个出口：**打开 pull request**，或者当它本身就来自某个 pull request 时，**推送到 pull request**。它不把工作落进你自己的检出，而是把分支推到 forge 上——而且对于来自 pull request 的任务，它是**取代**「合并」的，因为那份工作属于那个 pull request 的分支，而不是你的基线。如果这一次推回去**什么都不带**，它会被拒绝，并转而指向*完成*——对于一个结论是「不需要改动」的任务，那才是诚实的收尾。→ [把结果收回来](/zh/guide/repository#take-the-result-back)

### 说清楚你要的是哪一种「继续」 {#say-what-kind-of-follow-up-you-mean}

**继续处理**会先问你意图、再问你内容，因为同一句话可以是四件完全不同的事：

| 意图 | 它告诉智能体什么 |
| ------ | ----------------------- |
| **修改返工** | 把这里改掉。默认项，也是原先「打回」所做的事 |
| **继续推进** | 再做一件事——已经做完的部分原样保留 |
| **提问答疑** | **不要改任何文件**，只回答问题 |
| **自查验证** | 在我验收之前，你自己先过一遍 |

这个区分最值钱的地方是**提问答疑**：一个被告知工作「被打回」的智能体，无论如何都会开始改文件——而当你只是想问某个函数是做什么的时候，这恰恰是最不该发生的事。**自查验证**则是唯一一个可以**留空发送**的意图——「你自己看一遍」不需要多解释，而把它变成一次点击，本来就是它大部分的价值所在。

无论选哪一种，工作都会在同一个 worktree 中继续，然后再次回到验收。Codeg 会尽可能恢复原来的那个会话，让智能体保留全部上下文；若该智能体无法恢复会话，则会在同一个 worktree 中新开一个会话接手，并把任务本身和你的反馈一并重放给它，同时在推进记录中留下这次回退。

## 合并它 {#merge-it}

合并是**由智能体在它自己的会话中完成的**——正是这一点让它能够解决冲突，而不是把冲突甩给你。**合并任务**对话框问三件事：

- **提交信息**——**让智能体自动生成提交信息**默认勾选，智能体会根据实际改动写出一行 Conventional Commits 风格的信息。取消勾选即可自己写；输入框中已预填任务标题。
- **额外指令**（可选）——落地这件事是由智能体执行的，所以你可以给它方向：*「冲突时一律取本分支这一侧」*、*「顺手更新一下 changelog」*。留空则什么都不改变。你写的内容会**和这次合并一起被暂存**，因此一次[在队列里等过位置](#a-second-merge-waits-in-line)的合并，落地时依据的仍是你当初排队时给的那份指令，而不会把它弄丢。它被安排在收尾规则之前读到，这是刻意的——最后一句话仍然属于那些禁止推送、禁止自我删除的规则。
- **合并后删除 worktree**——初值取自该文件夹的任务设置。

**策略**不在这里问——它是在合并开始时从该文件夹的[任务设置](#task-settings)中读取的。**合并为一条提交**（squash，默认）把整个任务作为一条历史记录落地；**保留完整提交历史**则保留任务过程中的每一条提交，另加一条合并记录。想用另一种，请在合并之前先去那里改。

接着，智能体会把任务分支上尚未提交的内容提交掉，把基线分支合并*进*这个 worktree 并在那里解决每一处冲突，然后才把结果落到你项目文件夹的基线分支上。

这里面没有一步是 Codeg 听智能体一面之词的。回合结束时它会核对 **git 的事实**——基线分支的 HEAD 真的前进了吗？它真的包含这些工作吗？如果不是，任务会**退回验收**并附上原因，同时把任何做了一半的合并从你的项目文件夹里清理干净。

::: warning 合并对你的项目文件夹有要求
合并落地在你正在使用的那个文件夹里，所以它会先检查：该文件夹必须**位于基线分支上**，且**暂存区为空**。任何一条不满足，你都会拿到一句直白的说明，且什么都不会被改动。
:::

### 第二次合并会排队等着 {#a-second-merge-waits-in-line}

每个项目**同时只跑一次合并**——它们都要落到同一条基线分支上，因此无法重叠。以前，在一次合并进行中又验收通过第二个任务，会被直接拒绝；现在它会**排进队列**，并在档期空出来的那一刻自行开始。

- 卡片和列表行会显示**排队合并**，带上**它排在第几位**，并提供**退出队列**的方式。
- **再次提交会更新那次排队中的合并**——换一段提交信息、换一个 worktree 处理方式——而不是再排一个，并且保留原有的位次。
- **撤回就是真的撤回。** 一次被你移出队列的合并，不会再被某个还在按旧视图工作的后台扫描落地。
- 你手动排的队会**优先于自动合并**执行，因此你亲手要求的合并绝不会被文件夹自己的日常整理挡在后面。

### 让文件夹替你落地 {#let-a-folder-land-them-for-you}

文件夹「合并」设置中的**自动合并**，做的正是你点**合并**会做的事——同样由智能体撰写提交信息，同样应用按阶段的提示词，同样沿用删除 worktree 的默认值。打开它的文件夹会自己把验收那一列排空，从最早落定的开始，一次只合并一个。

它刻意不做的，是硬闯过一个问题：

- **预检为红灯或尚未出结果时，会留给你。** 只有绿灯才算合格；没有配预检命令时，则根本没有这道关卡。
- **没有任何改动的任务不会被动**——那是*完成*的地盘，由你来判断。
- **worktree 已丢失的任务同样不会被动**，理由相同。
- **你用「以后处理」放到一边的任务不会被动**，直到你把它拿回来。
- **失败会在卡片上留下提示并停下。** 它**绝不会无人值守地重试**——失败过一次的合并只会循环地失败下去，所以这一行会等一个人来处理，而这一轮扫描继续往下走。

## 任务设置 {#task-settings}

**任务设置**对话框（右上角那一簇里的滑块图标）有一个**作用域**开关：**全部文件夹（全局默认）**，或某一个特定的文件夹。一个文件夹要么**使用全局默认**——那边一改，这边自动跟着变——要么有自己的**单独配置**；而切到单独配置时，它会从今天实际生效的那套值开始。

其下分为四个标签页，一个标签页管一件事：

| 标签页 | 设置 | 作用 |
| --- | ------- | ------------ |
| **常规** | **默认 agent** | 此文件夹中的任务所使用的智能体，除非某个任务另行覆盖——它的模型、模式和选项与 composer 一样，放在同一个智能体设置按钮上 |
| | **自动处理** | 待办自行开始，受并发上限约束 |
| | **最大并发任务数** | 同时运行多少个，按文件夹计。默认 **2**；`0` 表示不限制 |
| **合并** | **默认合并策略** | squash 还是完整历史，以并排的两个选项呈现。在合并开始时读取——合并对话框不会再问 |
| | **自动合并** | 不用点击就落地已验收的任务——见[上文](#let-a-folder-land-them-for-you) |
| | **合并后删除 worktree** | 在合并对话框里默认勾选那一项；到时仍可临时改 |
| **Worktree** | **Worktree 位置** | 新的任务 worktree 建在哪里——见[下文](#keep-the-worktrees-somewhere-else) |
| | **Worktree 初始化命令** | 在新建的 worktree 中、智能体开始之前运行 |
| | **预检命令** | 任务抵达验收时在 worktree 中运行——那盏验收灯 |
| **提示词** | 按阶段追加的说明 | 见下文 |

在 0.26 之前，「合并」与「Worktree」还合在一个**流程**标签页里——它们回答的是两个不同的问题（一个做完的任务怎么落地，以及它的工作发生在哪里），如今各自独立。存储的内容一点没变，而且**切换标签页不会丢掉你的编辑**，所以你可以三个页签都填好，最后保存一次。

### 把 worktree 放到别处 {#keep-the-worktrees-somewhere-else}

默认情况下，任务的 worktree 就**建在项目文件夹旁边**，作为同级目录。这是最不让人意外的位置，但也意味着一个装满项目的文件夹会在 `myapp` 边上长出一个 `myapp-task-7`。

Worktree 标签页上的 **Worktree 位置**接受一个目录，改为把它们都放进去——每个任务在其下一个 `<仓库>-task-<id>`，可以用操作系统的对话框或应用内的浏览器来选。`~` 是你的主目录，而**相对路径以项目文件夹为基准**解析。把它设成全局，就能把所有项目的任务 worktree 收拢到一处——比如 `~/codeg-worktrees`；也可以只为那个同级布局碍事的仓库单独设置。

**留空**则一切照旧：worktree 继续落在项目旁边。改动它也只影响以后——**已经在磁盘上的 worktree 会原地不动**，因为任务复用的是当初分配给它的那个检出。

### 在恢复的一轮之前先压缩 {#compact-before-a-resumed-round}

一个来来回回跑第二、第三、第四轮的任务，每次都在往同一个上下文窗口里填东西，而最终撑爆的那一轮，往往正是你在意的那一轮。从 **0.30.0** 起，任务可以先把自己压缩一下。

两项设置：一个按百分比的**自动压缩阈值** —— 上下文要满到什么程度才值得做 —— 其中 **0** 表示关闭；以及一个可选的**压缩命令**，用于你的智能体的压缩方式并不显而易见的情形。

当一轮**重试、跟进或合并**恢复了一个占用达到或超过阈值的会话时，引擎会先发出压缩命令，等那一轮落定，然后才发出这一轮自己的消息。**全新的会话永远不会被压缩** —— 那里没有东西可压。进去时读到的占用率会记到任务的时间线上，而压缩之后的那个数字，会在活着的会话确实报上来时一并记上，于是你能看出自己设的阈值到底有没有起作用。

命令按智能体解析，由具体到通用：你的设置，然后是会话自己声明的压缩动作，最后是一个内置默认值。只有当某个智能体的压缩方式无法被发现时，才需要你去设它。

### 按阶段追加你自己的说明 {#add-your-own-instructions-per-stage}

每一次启动都已经带着一段内置提示词——任务本身、worktree 规则，合并时还包括具体的 git 步骤。**提示词**标签页就是你往上添内容的地方：选一个阶段，写下你的项目所需要的东西，你的文字会以*补充说明*为标题**追加**在 Codeg 自己那段措辞之后。它是对内置内容的细化，绝不会替换它们，所以其中任何一条你都不必重述。

一共五个阶段，各自带有自己的示例占位文本，已经写了内容的阶段会带一个圆点：

| 阶段 | 何时发送 |
| ----- | --------- |
| **全部阶段** | 智能体收到的每一段提示词，包括合并那一轮 |
| **任务执行** | 任务首次执行时 |
| **重试执行** | 重新接手被中断或失败的任务时 |
| **继续处理** | 你对一个待验收的任务继续处理时——返工、追加工作或自查 |
| **合并变更** | 智能体把任务合并到基线分支时 |

这样拆分是有价值的，因为适合放进某一个阶段的内容，和适合放进另一个阶段的完全不是一回事。*全部阶段*适合放通用规矩——*"遵循 AGENTS.md 中的约定；最终总结不超过两句话。"* **继续处理**才是写 *"逐条处理反馈中的每一点；不要顺手重构无关的东西"* 的地方。而 *"落地提交信息用英文；手工解决过的冲突要说明"* 只在**合并变更**阶段说得通，放在别处都没有意义。

## 让看板保持整洁 {#keep-the-board-tidy}

- 用工具栏里的**搜索任务**框来**搜索**——自 **0.35.2** 起，看板和列表都可以用。它随输入即时筛选、不区分大小写，并要求你输入的**每一个词**都在某处匹配上：标题、分支、文件夹、智能体，以及描述——如果是来自[仓库面板](/zh/guide/repository)的任务，则换成它的仓库、工作项编号、工作项标题和 URL。**`#12`** 是精确匹配——编号为 12 的任务，或者由 issue 或 pull request 12 创建的那个——而光写 `12` 还会找到 #112。没有剩下任何卡片的列会显示**无匹配**，列表视图提供**清除搜索**，按 Escape 也能清空，而且每次打开待办任务时，搜索框都是空的。
- 用下拉框**按文件夹筛选**，在列表视图中按状态筛选，用**筛选**菜单按可见性筛选：**显示已取消**（默认开启）和**显示已归档**（默认关闭）。当你偏离了这两个默认值时，筛选按钮会自己带上徽标。
- **文件夹选择器支持搜索。** 它就是新建对话的 composer 所用的那个列表——一个搜索框，每个文件夹一行，显示为*别名 [ 名称 ]* 外加它的完整路径。输入的内容会同时匹配别名、真实目录名**和**路径，因此两个被你起了相同别名的文件夹依然分得清，而一个你只记得磁盘名的文件夹也依然找得到。任务编辑器里的目标文件夹和设置的作用域选择器用的也是它。
- **归档**会在任务走到终点后——已完成、失败或已取消——把它从看板上拿走而不删除它；**全部归档**会清空已完成列当前显示的一切，只有留到以后处理的任务除外——它们会等着你来处理。已归档的卡片只提供一个操作——**取消归档**。
- **重新排队**把一个已取消的任务放回*待办*，并复用它的 worktree，同时可以附上一段说明，讲清楚这一次该有什么不同。
- **删除**会彻底移除一个任务，并先取消正在进行的运行，同时提供一个可选的复选框来**同时删除其 worktree**。
- **删除 worktree**——详情抽屉底栏上一个纯图标按钮，就在删除的左边。合并、完成，以及从 **0.28.2** 起的交付到 pull request，都会*询问*是否顺带带走 worktree，也都允许你说不，于是一个已完成的任务可能一直占着一份再也不会有人打开的检出。这个按钮回收那份磁盘空间，同时**不动任务本身**：目录和它的工作分支被删掉，卡片留在看板上，它的对话被重新挂到项目文件夹下。它会先要求确认，而且只在确实有东西可删、并且没有一次失败的清理已经在展示自己的重试按钮时才出现。
- 如果 worktree 无法被移除——有东西打开着它、有锁文件被占用——卡片会显示**清理失败**或**保留 worktree**，并提供**重试清理**。没有任何东西会被悄悄留下。
- **还存着未提交改动的 worktree 不会被移除。** 从 **0.30.0** 起，这次移除会被直接拒绝而不是强行执行，因为强行执行会把那些改动一起带走，而它们没有任何地方可以找回来。要么提交它，要么明明白白地丢掉它，然后再移除这个 worktree。

## 须知 {#good-to-know}

- **任务以项目为界。** 它们从项目根目录运行，绝不从 worktree 运行；一个任务的看板就是该文件夹的看板。
- **每个任务都是一个完整的智能体会话。** 有它自己的令牌开销、自己的记录、在你历史中自己的条目。同时跑四个，就是四个会话的花费。→ [Token 用量](/zh/guide/token-usage)
- **在服务器上同样可用。** 任务引擎在桌面应用和 [`codeg-server`](/zh/getting-started/deployment) 中都会运行——每个数据目录只有一个引擎，因此共享同一个数据目录的桌面应用与服务器不会同时驱动看板。
- **重启不会丢工作。** Codeg 退出时正在运行的任务回来后会标记为*已中断*，而**重试**会在同一个 worktree 中继续——那里面还留着智能体已经做完的一切。
- **重试是从干净状态开始的。** 它不会再带着上一轮运行给自己写下的那份结果。
- **删除 worktree 不会删掉它的对话。** 这些对话会被重新挂到项目文件夹下，而且 Codeg 记得它们最初是在哪里运行的，因此它们的历史依然能被解析出来。
- **基线在创建时就钉住了。** 任务是相对于其 worktree 分出来的那个提交做 diff 的，而不是相对于你的分支此后漂到的位置——这也正是合并那一步要先把基线合*进来*的原因。
- **来自仓库工作项的任务永远不会自我合并。** 它的提示词里带着开这个 issue 的人写下的文字，因此它被排除在该文件夹的无人值守巡检之外——这是一条**规则**，而不是一个你能关掉的设置。来自 issue 的任务仍可由你点击合并；而来自 **pull request** 的任务根本不能在本地合并，它给出的是「推送到 pull request」。→ [仓库面板](/zh/guide/repository#the-rules-that-do-not-bend)
